Client file

inputs/SCENARIO_B_EUROFREIGHT_LOGISTICS.json

The raw intake: a profile, free-text platform signals, free-text internal context, and optional telemetry with sector peer benchmarks.

Why this shape

  • Text and numbers stay apart: free text goes to the LLM, which handles wording; metrics go to code, which handles arithmetic.
  • Requests are just input: leadership asks sit in their own field and are judged later (step 07), never followed blindly.

01

Input repair

Codeinput_check.py · sanitize_client()

Turns any client file into the one shape the engine expects, and logs every change as a warning. It never stops the run.

Why this stage

  • Real intakes are messy: a misnamed section or "18%" as text should not crash a client's run.
  • Nothing changes silently: every fix is a warning in the trace and in the GUI.
  • One contract: the CLI and the GUI upload accept exactly the same files.
  • Graceful fallback: with no usable metrics the engine still plans from text instead of failing.

Receives

The raw file in any of three wrappers: engine format, flat dataset scenario, or blind_judge_scenario.

// a messy example (not EuroFreight)
"internal_contex": "…"
"metrics": { "t0": { "…_dropoff_pct": "18%" } }

Does

  • Unwraps the blind-judge wrapper
  • Drops the challenge's own summary and key questions
  • Maps misnamed sections by spelling (0.75 cutoff) or a hint word
  • Flattens wrong types to text
  • Converts "18%", "3,4", "1.234,5" to numbers
  • No usable T0 metrics: the run becomes text-only

Sends

client = {profile, ingaze_platform_signals,
          client_internal_context, metrics?}
warnings = [
 "section 'internal_contex' read as
  'client_internal_context'",
 "metric '…_dropoff_pct' = '18%' given as
  text: read as 18" ]

EuroFreight: already clean, 0 warnings.

↓ passes clean client; text goes to step 02, metrics to step 04
02

Read facts

LLM × 3extract.py · settings in knowledge/reading.yaml

The only step that reads client text. Three runs in parallel, then code keeps what at least 2 runs agree on, checks every quote is verbatim, and applies the context filter.

Why this stage

  • Paraphrase needs a reader: "6-month churn" and "first-year turnover" mean the same thing; a keyword list misses this (we tested 11 tricky sentences).
  • Typed facts let code decide: after this step, code reasons over fact kinds, not raw text.
  • No invented evidence: a fact whose quote isn't in the input is dropped.
  • Stable reading: the 2-of-3 vote stops one odd run adding or removing a root cause.
  • No off-topic evidence: "customer churn fell to 3%" is not read as staff churn.

Receives

Every text field, labelled with its path:

[ingaze_platform_signals.recruiting_and_jds]
"…63% of visitors drop off before completing
 the application form because it requires
 desktop-style account registration and a
 5-page CV upload."

Does

  • Splits text into atomic facts of fixed kinds
  • Gives each fact a status, a subject (who) and a time (when)
  • Drops any fact whose quote isn't in the input
  • 2-of-3 vote on kind + subject + polarity
  • Only current facts about employees, candidates or managers can be used as evidence
  • Also reads workforce cohorts, euro costs and request details

Sends

F8  recruiting_symptom · candidates · current
    "63% of visitors drop off before…"
F9  application_friction · active   vote 3/3
    "…requires desktop-style account
     registration"
W1  drivers · deskless_frontline · mobile_route
W2  warehouse ops · frontline_shift  vote 2/3
E1  €190,000 per quarter on agencies
F25 leadership_request · Regional Hub Directors
    lever: mobile_fast_apply · urgency: immediate
    skipped: "portal UX or persona audits"
↓ passes 26 facts (F1–F26), workforce cohorts, 1 cost item, noticed sentences
03

Double-check and coverage

LLMCodeextract.py · double_check, coverage()

Facts that could block advocacy get a second, narrow LLM reading. Code then compares the two readings and checks that every noticed sentence became a fact.

Why this stage

  • These facts are costly to get wrong: they decide whether advocacy is allowed.
  • It fixed a real error: our first version misread "the gap … is minimal (0.2 stars)" and blocked advocacy for three healthy test clients.
  • Fails safe: a disputed problem becomes a Phase 1 check, never silently assumed away.
  • Nothing dropped: the coverage check turns any unclassified sentence into an open question.

Receives

Each blocker fact (Say-Do Gap, burnout, management, shift burnout, early attrition) plus its sentence and 1 neighbour each side.

// CloudNova (EuroFreight has no blocker facts)
F6 say_do_gap
"a 1.3-star gap between external recruiting
 claims ('cloud autonomy') and recent
 engineering reviews citing 'rigid project
 micromanagement…'"

Does

  • Asks: present, absent or unclear? About whom? Current?
  • The deciding phrase must be verbatim
  • Readings disagree on a present problem: conflict, so it is verified, never assumed away
  • Absent vs unclear: unconfirmed
  • Noticed sentence linked to no fact: raised as a question

Sends

F6 double_check:
  first_reading:  present · employees · current
  second_reading: present · employees · current
  outcome: agree → F6 stays active

EuroFreight: 0 blocker facts to re-read, 0 unclassified sentences.

↓ passes confirmed facts; merged with signals into one set of tags
04

Signals

Codesignals.py · knowledge/metrics.yaml

Runs alongside step 02. Compares each client metric with its sector peers, checks fixed thresholds from the dictionary and research, and turns each result into tags.

Why this stage

  • Numbers need context: 63% drop-off is a problem because peers are at 41.2%.
  • Every threshold has a source: the telemetry dictionary or a research snippet, so we can cite it.
  • Healthy signals matter too: they protect what works and rule out suspected causes, such as pay.
  • One vocabulary: tags are shared by causes, interventions and cases, so text and telemetry combine.

Receives

client  application_form_dropoff_pct  63.0
peers   application_form_dropoff_pct  41.2
client  compensation                   4.7
peers   compensation                   3.31
client  site ratings  Verona 4.31 … Naples 3.08

Does

  • Knows if higher or lower is better for each metric
  • Stars: 0.25 off = moderate, 0.5 = severe
  • Percentages: 15% worse = moderate, 30% = severe
  • Fixed lines, e.g. drop-off above 58% (R2)
  • Finds healthy and struggling sites

Sends

S7  drop-off 63 vs peers 41.2 (+53%, worse)
    severe → tag application_friction
S19 drop-off above the 58% level in R2
    severe → tag application_friction
S5  compensation 4.7 vs 3.31 (better)
    healthy → tag compensation_healthy
S25 Verona hub 4.31 vs mean 3.83
    healthy → tag healthy_site

Merged state (knowledge.build_state)

Facts and signals become one set of 31 tags, each with the evidence ids behind it, e.g. application_friction: [F9, F10, S7, S12, S19]. Implied kinds are added here too (shift_burnout also counts as burnout).

↓ passes tags + evidence ids (F# and S#)
05

Diagnose root causes

Codediagnose.py · knowledge/causes.yaml

Scores each of the 13 catalog causes from its evidence and gives it one status. Only direct evidence can create a cause; symptoms can only support one.

Why this stage

  • Causes, not symptoms: a 43-day time-to-hire is the symptom; the desktop-only form is the cause, and that is what gets fixed.
  • Consistent and auditable: a fixed catalog of 13 causes with scores means the same evidence always gives the same diagnosis.
  • Honest certainty: contributing and conflict causes become checks, not spending.
  • Restraint with proof: "pay is fine, 4.7 vs 3.31" saves budget and answers the CFO's first question (FN5).

Receives

Application form friction
  direct:  F9, F10, S12
  support: S7, S19, F8, F20, S8
Pay below market
  direct:  none
  healthy: S5 (4.7 vs peers 3.31)
Slow candidate follow-up
  direct:  F5  "slow candidate response"
  negated: F26 "HQ roles hire smoothly"

Does

  • Direct = 1.0, support = 0.5 each (max 1.0)
  • A quote-verified text cause is diagnosed unless contradicted
  • A telemetry-only cause needs a score of 1.5
  • Keeps the top 5; the rest become secondary
  • Suspected causes with healthy data are ruled out
  • Checks a stated euro total against its named drivers

Sends

Application form friction  diagnosed  4.0
Generic job ads            diagnosed  4.0
Manual tracking, no EMV    diagnosed  4.0
Channel mismatch           diagnosed  2.0
Unmanaged local reputation diagnosed  2.0
No candidate feedback loop secondary  1.5
Slow candidate follow-up   conflict   2.0
Pay below market           ruled out
Uncoached management       ruled out

Ruled-out line in the output: "Pay below market: compensation 4.7 vs peers 3.31 → no remediation spend".

↓ passes cause statuses to the gate, verdicts, skeleton and ranker
06

Advocacy gate

Codegate.py · knowledge/gate.yaml

Decides if employee advocacy may start (FN4, R5). Only a diagnosed or conflict blocker, or a telemetry blocker, closes the gate.

Why this stage

  • Advocacy amplifies the culture that exists: asking staff to promote the company during burnout or a Say-Do Gap causes backlash (FN4, R5).
  • One explicit state: the LLM can't promise an ambassador campaign while a blocker is active.
  • "Not yet" becomes a target: release criteria tell the client exactly what must improve.
  • Weak evidence doesn't stall the plan: a contributing blocker adds a check but never blocks alone.

Receives

blocker causes:  none diagnosed
claims gap:      0.31★ (limit 1.0★)
attrition:       14.6% vs sector 18.8%
healthy tags:    culture_healthy,
                 retention

Does

  • Any active blocker: BLOCKED
  • All 3 ready groups hold: READY
  • Otherwise: NEUTRAL
  • Writes release criteria from the client's own numbers

Sends

state: NEUTRAL
reason: no blocker, but not ready
ready conditions:
  employees already speak up   ✗
  the EVP is authentic          ✗
  the climate is healthy        ✓

CloudNova, for contrast

BLOCKED by a diagnosed Say-Do Gap, management friction and early attrition. Release criterion: "claims gap at or below 1.0★ (now 1.3★, sector peers 0.44★)".

↓ passes gate state + release criteria
07

Request verdicts

Codeverdicts.py · knowledge/verdicts.yaml

Each leadership request gets exactly one verdict. The strongest wins: BLOCKED, DEFERRED, RESEQUENCED, RESCOPED, NOT_SUPPORTED, ACCEPTED.

Why this stage

  • Requests are the planted traps: the engine must neither obey them blindly nor ignore them.
  • More useful than yes or no: "not yet", "after the audit" and "start with a pilot" give leadership something to act on.
  • A reason every time: each verdict comes with the rule and field note behind it.
  • The decision sticks: banned levers are removed from the plan and rejected by the verifier if they come back.
  • Result: 6/6 official request verdicts correct.

Receives

F24 Marketing Director
    "technical LinkedIn blog series
     to attract drivers"
    lever: technical_storytelling
F25 Regional Hub Directors
    "fast-apply widget … tomorrow morning"
    lever: mobile_fast_apply
    skipped: portal UX / persona audits

Does

  • Lever doesn't fit the workforce: BLOCKED
  • Would change a healthy asset or uses noise: BLOCKED
  • Advocacy while the gate is BLOCKED: DEFERRED
  • Urgent or skips a prerequisite: RESEQUENCED
  • Company-wide with site differences: RESCOPED

Sends

F24 BLOCKED
    "Technical storytelling does not fit
     the deskless_frontline workforce
     (FN2/FN6)"
    banned: technical_storytelling
F25 RESEQUENCED
    "Fast-apply comes after the Career
     Portal UX Audit instead of
     'tomorrow morning' (FN5)"
↓ passes verdicts + banned levers
08

Plan skeleton

Codeskeleton.py · knowledge/interventions.yaml, fit.yaml

Picks the actions and their phases. Every diagnosed cause gets a fix, prerequisites come first, misfits and banned levers are left out, max 5 per phase.

Why this stage

  • Stable structure: the same input gives the same actions in the same phases on every run.
  • Safe order: diagnose before you redesign (FN5); fast-apply waits for the portal audit.
  • Nothing left unfixed: every diagnosed cause gets a real fix by Phase 2.
  • Realistic size: max 5 actions per phase suits a small HR team (the first version had 8 phases over 5).

Receives

  • Cause statuses (step 05)
  • Gate state (step 06)
  • Verdicts and banned levers (step 07)
  • Each of the 24 interventions' status: relevant, not indicated, wrong workforce or blocked
  • Work settings: mobile_route, frontline_shift

Does

  • Selects actions that fix or verify a cause
  • Places each in the earliest phase after its prerequisites
  • Merges related diagnostics into one slot
  • Drops misfits with a logged reason
  • Advocacy waits for the gate

09

Rank past cases

Coderank_cases.py · knowledge/ranker.yaml

Scores all 21 library cases against the client and keeps the top 3, with real ROI and before/after numbers added by code.

Why this stage

  • Credibility: "a similar company did this and got these numbers" persuades a CFO more than theory.
  • Match on the problem, not the industry: root cause carries 55% of the score.
  • No wrong-sector playbooks: the fit penalty fixed a logistics test client getting retail cases.
  • No invented ROI: code copies the numbers from the case library.
  • No overfitting: weights were chosen by leave-one-out on the 21 cases, never on the 3 scenarios.

Receives

client tags: application_friction,
  generic_job_ads, multi_site_variance,
  slow_time_to_hire, agency_dependency, …
T0 metrics: drop-off 63, conversion 1.89, …
work settings: mobile_route,
  frontline_shift
sector: freight logistics

Does

  • Score = 0.55 root cause + 0.30 T0 numbers + 0.10 work setting + 0.05 sector
  • Rare shared tags count more (IDF-Jaccard)
  • Penalises cases whose actions don't fit this workforce
  • Band: strong ≥ 0.6, moderate ≥ 0.4

10

Write the plan

LLMplan.py

The LLM writes the words only: one 25–35 word line per slot, a sentence per diagnosed cause, the reason for each verdict, research citations and open questions. Code adds the standard action name in front.

Why this stage

  • Each part does what it is best at: the LLM writes clear, client-specific text; code has already made the decisions.
  • Specific, not templated: it names this client's cohorts and sites (C-CQC drivers, Bologna and Naples).
  • Checkable output: the tags on each action let code verify the wording in step 11.

Receives

slot A6 mobile_fast_apply · Phase 2
  why: Application form friction,
       resequenced request F25
cause application_friction · diagnosed
  evidence: F9, F10, S12
verdict F24 BLOCKED + code reason
+ top 3 cases, research R1–R10,
  field notes FN1–FN6

Does

  • Words each slot for this client's cohorts and sites
  • Tags each action: intervention id, advocacy flag, cohort, work setting
  • Uses only numbers it was given
  • Can't add, remove or move a slot

Sends

A6: "Mobile fast-apply pilot: After the
 portal audit, pilot mobile fast-apply for
 C-CQC drivers in Bologna and Naples,
 removing account creation and deferring
 the CV upload."

root cause: "Application form friction:
 C-CQC driver and Warehouse Operator
 applicants face desktop-style account
 registration and a five-page CV upload on
 a portal they primarily access by phone."
↓ passes draft plan + action tags
11

Verify the plan

Codeverify.py · tripwire.py

26 checks on the draft. Problems go back to the LLM for up to 3 rounds; anything still failing is removed by code and logged.

Why this stage

  • Trust, but check: the LLM is never relied on to follow the rules by itself.
  • Readable fixes: feedback rounds let the LLM correct itself in its own words.
  • Guaranteed safe output: code enforcement means no rule-breaking action reaches the client.
  • No made-up statistics: final audit found 0 ungrounded numbers.

Receives

The draft plan with its tags, plus every code decision: causes, gate, verdicts, skeleton, allowed numbers.

// CloudNova draft, round 1
action 3: "Audit Glassdoor and Indeed
 reviews for Milan and Berlin product
 squads…"
evidence_ids: [… F9 …]   F9 = noise row

Does

  • Fit: workforce and work setting
  • Gate, prerequisites, phase, allowed phases
  • Banned levers and healthy assets
  • Every number must exist in the input, research, cases or code
  • Tripwire: ~10 trap phrases, only a backup

Sends

round 1: 1 violation
  noise_usage · action 3
  "justified by noise fact(s) ['F9']"
  → sent back to the LLM
round 2: 0 violations
removed by code: none

EuroFreight: 0 violations in round 1, nothing removed.

↓ passes verified plan
12

Output

Codesubmission.json · trace/*.json, trace/*.html

The submission sections for the judges, plus a full trace of every step above for auditing.

Why this stage

  • Valid by design: the submission passes the official validator with 0 errors and 0 warnings.
  • Every decision is auditable: the trace links each claim to the quote or number behind it.
  • Repeatable demo: the LLM cache makes reruns identical, free and possible offline.

submission.json sections

  • diagnosed_root_causes
  • blocked_traps_and_guardrails
  • phase_1 / phase_2 / phase_3_actions
  • matched_case_studies
  • supporting_research_snippets
  • strategic_focus_and_do_not_touch
  • cohort_specific_strategies
  • open_questions_and_hypotheses_for_client
  • action_rationales

Example entries

blocked_traps_and_guardrails:
"[BLOCKED] Marketing Director request:
 Launch a B2B technical LinkedIn blog
 series to attract drivers. - Why: … a
 poor fit for deskless driver recruitment."

"[RESEQUENCED] Regional Hub Directors
 request: … (tomorrow morning) - Why: Audit
 the mobile funnel and calibrate driver and
 warehouse personas first."

Trace

One JSON and one clickable HTML file per client. It holds the facts and votes, double-checks, signals, cause scores, gate, verdicts, skeleton, case scores, verifier rounds and removals.

If a judge asks "why?", the trace shows the evidence ids behind each decision.

Examples are copied from the run traces in trace/. Two examples are marked as not from EuroFreight: the input-repair warnings (made-up messy input) and the double-check, gate contrast and verifier catch (CloudNova).
